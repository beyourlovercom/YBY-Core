## Native WooCommerce and paid vendor contract
Inspected exact locally owned WooCommerce 11.2.1, YayCurrency Pro 3.3.5, WebToffee Smart Coupons Pro 3.2.0 and StoreApps WooCommerce Smart Coupons 9.51.0 source. Private paid files remain local and not committed.

1. **Native coupon types:** StoreApps Store Credit uses `smart_coupon`; WebToffee Store Credit uses `store_credit`; WebToffee BOGO can use `wt_sc_bogo` or older `wbte_sc_bogo`. Native `free_shipping` coupon flag is separately protected. This means the old generic H2 type set `store_credit,bogo,gift` is not sufficient for real two-vendor protection.
2. `R10H3C_Reward_Protection_Shadow::classify` protects those exact known vendor types, native free-shipping and zero-amount coupons. Normal `percent/fixed_cart/fixed_product` positive discounts are classified as removable only when vendor version verification was supplied by a trusted server runtime and no unrecognized vendor custom metadata exists; unknown types/metadata/amounts fail closed. It does not depend on coupon code naming. Source is not loaded or registered by the plugin.
3. **Classic Woo form handler** `WC_Form_Handler::update_cart_action` accepts a POST `apply_coupon` with `coupon_code` in its own branch *without a corresponding branch-local nonce check*. A browser POST shape alone does NOT demonstrate authenticated user manual intent.
4. **Store API** `CartApplyCoupon::get_route_post_response` uses `POST /wc/store/v1/cart/apply-coupon` and calls `CartController::apply_coupon`; its route's `permission_callback` is `__return_true`. Actual Cart-Token/session/nonce authorization resides elsewhere in the Store API/request lifecycle. Observing a matching `WP_REST_Request` path alone is NOT a server-signed manual customer provenance proof.
5. `R10H3C_Manual_Request_Shadow` recognizes these two request shapes as *candidates only*, always returning `manual_origin_verified=false`, `replacement_authorized=false`, with no writes. It intentionally cannot authorize a real coupon swap; future H3-C adapter needs request-scoped server validation and nonce/cart-token/session binding before creating a one-use manual intent.
6. Existing Woo `WC_Cart::apply_coupon` and Store API `CartController::apply_coupon` differ in apply ordering and individual-use behavior. Any eventual manual transaction must respect both and preserve prior vendor veto; no generic post-apply coupon removal callback is safe to attach yet.

## Full-fidelity rollback gate
`R10H3C_Full_Rollback_Shadow` captures **ordered** coupon list, native Woo cart totals (subtotal, discount, shipping, tax, total), Woo notices, auto-applied history for both paid vendors, StoreApps candidate cache and chosen shipping method. Snapshot normalization denies unknown objects and oversized data. Strict comparison detects changes in any of those fields; it does not mutate the cart or restore a snapshot. This is *detection only*, not proof of a working late-failure rollback transaction. Earlier H3 sandbox proved naive remove/readd changes coupon order, and that unsafe workaround remains forbidden.

## Honest blockers / NEXT gate
**H3-C IS NOT COMPLETE** despite passed source gates:
- **Authentic manual intent**: still missing separately owned, one-use and server-verified Classic Cart and Blocks Store API request-bound token/session lifecycle with vendor compatibility. In particular, matching route/POST body is not enough.
- **Actual protected reward behavior**: types/metadata verified, but *real Store Credit consumption, gift quantity, BOGO eligibility and individual-use paid vendor interactions* are not yet acceptance tested end-to-end.
- **Real five-currency transaction paths**: local licensed Woo sandbox has source Woo default currency USD but no five currency YayCurrency configuration or rate fixtures loaded; cannot claim genuine USD/EUR/GBP/AUD/CAD live coupon/credit/shipping/checkout parity. Existing CI five-currency synthetic/other runtime tests do not substitute exact paid two-vendor transaction proof. No invented exchange rates.
- **Atomic post-commit failure recovery**: snapshot *detection* exists, yet robust provider-aware restoration preserving exact coupon order/Store Credit state/Woo totals/notices is not built or accepted; any late failure still a HARD BLOCKER.
- Classic Cart/Blocks and REST customer request flows must be tested under actual nonce/cart-token rules with authorized owned disposable environment (not a forged client flag).
