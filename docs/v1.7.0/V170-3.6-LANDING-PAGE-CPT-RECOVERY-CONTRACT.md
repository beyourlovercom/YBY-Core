# V170-3.6 — Landing Page CPT Recovery Contract

## Product goal

Restore the standalone Landing Page content model remembered from the pre-governed Andy Core era.

Landing Pages are first-class WordPress content used primarily for advertising, campaign, and conversion-focused pages.

They are not Project Studio records and are not ordinary WordPress Pages.

## Historical recovery limitation

The currently available Git history, reflog/unreachable commits, release ZIPs, Local backups, current Local database, and rewrite rules do not contain the original Landing Page CPT implementation or its historical internal post type slug.

Because the old internal slug cannot be proven, v1.7.0 does **not** guess or reuse an unverified legacy post type name.

The public URL contract is the compatibility surface that matters and is restored exactly.

## Canonical identifiers

- module id: `landing_pages`
- internal post type: `yby_landing_page`
- public rewrite slug: `lp`
- canonical public URL: `/lp/{slug}`
- rewrite version option: `yby_landing_page_rewrite_version`
- rewrite contract version: `1`

The internal post type is namespaced to avoid collisions with third-party plugins that may use generic names such as `landing_page`.

## WordPress content behavior

Landing Pages are:

- public
- publicly queryable
- excluded from ordinary site search
- non-hierarchical
- archive disabled
- REST/block-editor enabled
- managed with page-like capabilities

Supported editor features:

- title
- editor
- featured image
- excerpt
- revisions
- custom fields

## Admin IA

Landing Pages do not register a WordPress top-level menu.

Visible path:

`Andy Content → Landing Pages`

The submenu opens:

`edit.php?post_type=yby_landing_page`

The native WordPress list screen provides Add New / Edit / Trash / Publish lifecycle.

Landing Page edit and create screens keep Andy Content / Landing Pages highlighted through the canonical parent/submenu filters.

## Module Registry

Registry V2 metadata:

- name: `Landing Pages`
- default enabled: `true`
- status: `ready`
- capability: `edit_pages`
- admin parent: `yby-content`
- navigation URL: `edit.php?post_type=yby_landing_page`

Fresh installs therefore expose Landing Pages automatically.

## Existing-site adoption

Existing Andy Core sites may already have a materialized `yby_core_enabled_modules_v1` option.

A generic one-time Registry adoption seam is used:

`YBY_Module_Registry::adopt_default_modules_once()`

v1.7.0 adoption id:

`v170_landing_pages`

Rules:

1. If the enabled-module option does not exist, keep using Registry defaults and only write the adoption marker.
2. If an explicit module list exists, append only `landing_pages`.
3. Do not re-enable any previously disabled module.
4. Record the adoption marker in `yby_core_module_adoptions_v1`.
5. After the owner later disables Landing Pages, the completed adoption marker prevents forced re-enable.

This is a system configuration migration only. It performs no business-data writes.

## Rewrite adoption

The CPT registers on `init`.

On the first admin request for rewrite contract version 1:

1. register the CPT
2. flush rewrite rules softly
3. persist `yby_landing_page_rewrite_version=1`

Subsequent requests perform zero rewrite flushes until the rewrite contract version changes.

## Project Studio relationship

Project Studio may later reference or assign a Landing Page.

Project Studio does not own, create, or store the Landing Page content model.

## Template OS relationship

Template OS will later provide reusable presentation / assignment capability for Landing Pages.

V170-3.6 intentionally does not add speculative template metadata, version UI, iframe preview, or assignment records.

## Scope boundary

Not included in V170-3.6:

- Template OS
- template assignment
- special landing-page rendering engine
- custom HTML/CSS/JS editor
- campaign analytics UI
- page duplication UI
- legacy data migration from an unknown historical post type

Those require separate contracts.

## Validation

Required PASS gates:

- CPT registers as `yby_landing_page`
- public rewrite is exactly `/lp/{slug}`
- no top-level Landing Page menu
- Andy Content → Landing Pages exists
- block editor / REST enabled
- archive disabled
- ordinary site search exclusion enabled
- page-like capability mapping
- one-time rewrite flush is idempotent
- existing-site module adoption appends only Landing Pages
- completed adoption never force-reenables the module
- Docs / Registry / Runtime regressions remain green
