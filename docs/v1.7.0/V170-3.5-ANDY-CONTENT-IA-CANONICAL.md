# V170-3.5 — Andy Content IA Canonical

## Product decision

`Andy Content` is the canonical WordPress admin home for Andy Core-owned standalone page/content products.

It sits beside the native WordPress content menus and collects the page-level systems that would otherwise fragment the left navigation.

## Canonical top-level IA

- Posts
- Pages
- **Andy Content**
- ...
- **Andy Core**

`Andy Content` uses:

- display label: `Andy Content`
- stable menu slug: `yby-content`
- capability: `andy_core_settings_manage`
- WordPress menu position: `21` (immediately after Pages at position 20)

## Current visible children

Only implemented products may appear:

- Overview
- Docs
- Landing Pages

No empty placeholder submenu is allowed for an unimplemented product such as Templates.

## Page/content ownership rule

Future Andy-owned products that create or manage standalone page-like content should declare:

`admin_parent => yby-content`

Examples include:

- Docs / Help Center content
- Landing Pages
- reusable Templates
- future page-level content types explicitly approved by Owner

These products may remain separate post types, modules, storage contracts, or plugins. The shared menu parent is an information-architecture decision, not a requirement to merge their data models.

## System ownership rule

System/runtime capabilities remain under `Andy Core`, including:

- Project Studio
- Inquiry / Lead runtime
- Email OS
- Social Login
- Connector / WP-API
- Module Registry / settings
- Security / updater / infrastructure

A page-like product should not be promoted to a new WordPress top-level menu unless Owner explicitly approves an exception.

## Andy Docs migration

Andy Docs keeps all stable identifiers:

- module id: `docs_os`
- dashboard slug: `yby-docs-os`
- all docs: `yby-docs-all`
- editor: `yby-docs-editor`
- directory: `yby-docs-directory`
- settings: `yby-docs-settings`
- post type / taxonomies / options / capabilities: unchanged

Only the admin IA changes:

- before: Andy Docs top-level menu
- after: Andy Content → Docs

Docs detail routes remain valid but are hidden from the WordPress submenu and keep Andy Content / Docs highlighted through `parent_file` and `submenu_file` filters.

## Landing Page recovery

Landing Page CPT Recovery is implemented by V170-3.6 and registers under Andy Content.

Canonical product semantics:

- module id: `landing_pages`
- internal post type: `yby_landing_page`
- standalone ad / campaign landing pages
- canonical frontend path: `/lp/{slug}`
- independent content lifecycle
- future template assignment through Template OS

Project Studio may reference/assign a Landing Page but does not own the Landing Page content model.

## Template OS

Template OS will also register under Andy Content when implemented.

Template OS remains a separate module/data model and is responsible for reusable presentation/templates, versions, assignments, and future page/module rendering contracts.

V170-3.5 does not create an empty Template menu.

## Registry V2 extension

Registry V2 normalized metadata includes:

- `admin_parent`

For Content-owned products:

`admin_parent = yby-content`

This allows future adapters to declare Content IA ownership without modifying the Core top-level menu implementation.

## Validation

PASS requirements:

- only Andy Content is registered as the content top-level menu
- Andy Docs does not register a top-level menu
- Andy Content position is 21
- Docs is a visible child of Andy Content
- Landing Pages is a visible child of Andy Content after V170-3.6 recovery
- stable Docs routes remain registered
- no empty Templates menu before Template OS implementation
- Registry V2 preserves `admin_parent=yby-content`
